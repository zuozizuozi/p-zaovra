## 推荐执行顺序

1. **补齐可复现的工程门槛。** 明确 main/dev 实际受支持入口，完善现有工作流的包覆盖与必需检查；Core/LLM/Client 跑已有相关测试，Schema 做类型和消费端契约检查，Desktop 接入健康单测与最小启动冒烟。使用正常构建，不发版。冻结修复前后源码及测试证据。验收：日志可证明每个要求的任务实际执行，无空任务冒充绿色；测试失败可阻止相应交付入口。远端保护设置需另行核实，单改 YAML 不等于启用门槛。

2. **补齐跨轮验收范围和证据适配。** 先用不计费本地用例复现“原题含 README → 用户只说继续 → README 缺失仍进入完成判定”的路径，再改现有 Outcome。稳定条款引用由 sourceMessageID 与不可变原文片段产生；同一工作延续保留原要求，明确修订保留来源关系。先定新任务与继续/修正的范围规则，不能把全 Session 历史要求永久累加，也不能靠模型独自决定 superseded。实现只涉及验收范围，不新增任务调度或 Agent 编排。新增具体需求/证据兼容检查沿用 Check，所有状态由宿主派生。验收覆盖继续、修正、明确开始新任务、两次压缩、事件重放、需求撤销、测试后改产物、修改失败断言、无关绿色命令冒充 README。对无法判定的范围显示未验证，不冒充已验证。

3. **工具权限边界作为独立小包。** 基于 PermissionV2 与 ToolRegistry 对明确的只读模式进行宿主约束，禁止写工具和任意 bash；拒绝后说明可用替代动作，允许正常继续。范围要覆盖插件/MCP，不能只隐藏内置工具。自由文本含“只读”不自动等同已可靠转换为策略，先明确结构化授权入口。验收：禁止调用零副作用、允许的读操作可继续、被拒绝/截断输入不会执行；正常实现模式不受误拦。

4. **先定向回归，再做完整对照。** 上述修改先跑固定本地故障与验收集，再申请少量真实任务：跨轮 README、CSV、库存及小游戏。需要证明交付率改进时，冻结旧/新 Zaovra 至少各五次，交错执行、隔离环境、全部计入，不遇失败重抽样本。Cline 先沿用历史参照；只有重新评估换内核才追加当期 Cline 组。共享同一模型接入、题目、初始文件、用户权限与独立判题，保留各自原生工具差异；记录实际 wire 参数，不能只凭配置叫严格等参。旧版当前重跑优于把历史结果当同期对照，无法运行旧版时明确降级为历史比较。

5. **随后做中断/副作用故障注入和验证工具扩充。** 从可见终态与禁止盲目重放开始，覆盖发请求前后、工具执行后落库前、后台命令未结束及桌面重启。先取得故障证据，再决定必要的持久状态新增。第一方浏览器验证工具以是否减少驱动错误、是否产出可审计事实为准，不一次上齐八个新工具。

## 验收口径

- False Verified、False Failed、Silent Stop 的分母和判定标准在测试前冻结；任意观察到的 False Verified 阻止该候选版本过门槛。零样本失败不等于总体失败率为零。
- False Verified（产品状态错误）与模型文字声称完成分开统计，避免把比赛旧 Fake Completion 定义直接当成同一指标。
- 安全指标与交付指标分开：全部标未验证也可能做到 False Verified=0，但不是改进；同时看完整交付率、人工介入、误拦、耗时、已知/未知 Token。
- 少量重复只能作为工程回归证据，不声称统计显著或适配所有模型。游戏须有真实操作及独立判题，README 等交付物单独检查。
- 发生公开 Schema/Protocol/HttpApi 变更时走正常 Client 生成流程，不手改生成文件。
