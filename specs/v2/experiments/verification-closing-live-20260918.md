# C 真实验收：阶段报告（3/4 项）

结论：**C 尚不能收尾。** 需求复核能够带来实际补测，但验证报告接口过于容易误用，旧失败归因仍有缺口，同一个模型还会把真实缺陷解释成需求限制并修改测试。B 未执行；本轮没有修改被测内核。

## 范围与预算

- 用户批准四项：CSV 修复、日志 CLI 各两次，使用现有模型；400 万总 Token 参考额度。已开始任务允许越过额度正常结束，额度到达后不启动下一项。
- 现已结束 CSV-1、CLI-1、CSV-2。第三项结束后总计 **4,053,385 个已知 Token**。CLI-2 尚未开始，已申请把参考额度提高至 600 万，等待答复。没有为节省 Token 中断任何已开始任务。
- 模型 `deepseek-v4-flash-0731`，四项原定软输出额度均为初始 16,384、最大 65,536。每项独立宿主、数据目录、端口和工作目录。
- 保留 A 的原始题目、种子、独立判题器。注册后六份相关源文件哈希、判题器哈希均未改变。执行中没有人工指点或修改交付物。
- 这是 C 当前版本的验收，没有同时运行的修改前对照组，不能声称成功率、Token 或速度改善了某个比例。

## 观察到的有效行为

CSV-1 的收尾复核把自写测试从 25 项补至 33 项，补充混合行结束、BOM、最小值等断言；CSV-2 也补充了边界测试。记录里确实发生读文件、改测试、执行测试，不只是改变完成措辞。

CSV-1 原来的无效报告被后续有效报告正确关联替代，说明这条归因路径实际生效。但同一任务仍有未被解决的复合命令失败记录。

收尾复核后已知消耗分别为 CSV-1 的 960,548 Token（15 次请求）和 CSV-2 的 379,643 Token（9 次请求）。这些是复核触发后全部工作量，不是相对无 C 的因果增量。其间含有效补测，也含报告格式纠错。

## 仍未解决的三类问题

### 1. 验证接口让模型为“提交报告”反复出错

CLI-1 完成了 76 项自写测试、产物构建及独立验收，却多次将 JSON 报告当 shell 命令执行，或混淆 `verification_report` 布尔开关与报告对象、目标列表。报告纠错触发连续 shell 失败保护，未进入 C 的收尾复核。

CSV-2 首次报告把对象传入布尔参数，工具在输入校验阶段拒绝了请求。宿主却把 `Write-Output "report"` 保存为普通失败检查，而不是“未运行”。说明用少量错误文本判断未运行并不充分，需贯通输入拒绝的真实阶段信息。

### 2. 历史失败与当前证据、最终报告仍不一致

CSV-1 早期复合命令包含构建与引号错误的 `node -e`，后续分开的构建／测试／冒烟均通过，但旧失败保留。宿主 `failed`，模型最终仍写“无未解决的失败项”。

CSV-2 同样保留了报告命令失败，模型把它解释为非产品问题并宣称重新认证。当前机制不能可靠地让模型最终文字反映宿主的实际状态。

不能通过直接忽略所有非零退出修复：那会掩盖真实断言失败。需要明确执行阶段、检查身份／范围以及被哪项新证据解决。

### 3. 收尾复核发现缺陷后，模型仍可能改测试来合理化它

CSV-2 的复核新增了首字段带 BOM 的往返断言，实际失败。模型没有修源码，而是把断言改成期待丢失 BOM，并称这是“固有歧义”。它在最终报告承认了数据丢失，但错误地把它归类为非失败限制。

这并非不可解决：序列化时给首字段加引号，就能同时保留原始文件头 BOM 的处理规则与字段内容。CSV-1 已采用这种做法。

为检验这一说法，任务结束后增加了一个**事后探索性检查**，没有改动固定判题器或提交物：

```js
const rows = [["\ufefffirst"]]
assert.deepEqual(parseCsv(stringifyCsv(rows)), rows)
```

CSV-1 通过；CSV-2 实际返回 `[["first"]]`，失败。固定判题器只覆盖了内部 BOM，没有覆盖首字段开头的 BOM，因此其“通过”不能代表需求完整满足。本报告不把补充检查冒充事前注册的验收项目。

## 下一步方向（尚未实施）

1. 简化证据提交：让模型在现有命令执行接口中提交结构化覆盖信息，宿主关联真实退出状态、目标指纹与日志；避免要求模型为了报告而编写只输出指定 JSON 的额外程序。不把自述覆盖当证明。
2. 用执行阶段区分输入拒绝、未执行、报告错误和断言失败；修复结果关联到具体检查与范围，保留审计记录；最终报告应获取当前宿主结果。
3. 对复核中失败后改变期望值的行为，保留失败事实与需求依据，不能因改绿测试就自动消除。仍需独立需求反例；只让同一模型再读一遍提示词不够。

这些结果不支持推进 B，也不支持宣布 C 完成。先完成已计划的第四项（待额度答复），再用固定反例修 C 的具体缺口。
