## 行为

在既有 SessionRunner 中处理单轮 `length`，不另建 Agent Loop、Retry 或恢复框架。每个 Provider Turn 仍只调用一次 `llm.stream`。原因分为推理耗尽、含工具的输出截断、空输出截断；纯文本延续保留原有独立规则。

1. 已知输出容量、上下文容量及当前额度时，下一轮最多翻倍，受模型容量、用户硬限制和上下文余量共同约束。上下文使用现有估算与本轮实报输入/输出，另留 4096 Token 余量；这不是精确 tokenizer，也不能替代已有压缩与溢出处理。
2. 无法扩容时，第一次允许保留上下文、工具及已完成结果，尝试更小的下一步。未完成的工具参数标记失败并交给模型重新生成完整调用，绝不拼接执行半段 JSON。已完成工具不由宿主自动重放；模型新提出的调用仍受既有权限和循环检测约束。
3. 同一原因、没有可观察文件变化时，最多调整两轮；无额度变化的较小步骤策略只尝试一次。它不是无限重试。已有 Provider Turn 限制、累计预算、取消和错误处理继续有效。
4. 恢复计数来自持久化事件，压缩、重放和新 drain 不重置。新用户输入或快照记录的文件变化才更新恢复机会。文件变化仅代表可观察的变动，不代表任务已完成；读操作、普通文本或进程退出码不清空计数。禁用快照时不会靠猜测恢复机会。
5. Provider 自己执行的工具涉及未知副作用，本轮不自动恢复；网络错误、内容过滤、未知结束原因不伪装成输出不足。不自动降低推理档位、关闭思考或删除不支持的参数来掩盖配置错误。

## 配置语义

- 模型 `limit.output/context` 描述容量，不是本轮实际额度，也不代表网关已验证的能力。
- 已有显式 `request.body.max_tokens`、`maxTokens`、`max_output_tokens`、`max_completion_tokens` 一律视为用户硬上限，统一映射到协议的原生输出字段。不同别名冲突、非正整数直接报配置错误。
- 可选的 `session_output` 提供软起始额度与硬上限。按实际 Provider ID 和 API Model ID 精确匹配，不根据名称猜模型。示例仅解释配置，不已写入生产设置：

```json
{
  "session_output": {
    "provider-id": {
      "api-model-id": { "initial": 16000, "maximum": 64000 }
    }
  }
}
```

显式请求上限及已知模型容量仍优先约束它。例如保留 `max_tokens: 16000` 时，该配置不会让请求越过 16000。要启用较大的软额度范围，必须先确认网关容量，并明确移除或调整旧的硬限制。未知输出容量时，显式 `maximum` 可作为操作者提供的上界；缺少上下文容量仍不自动扩容。没有配置时保留 Provider 默认，只有实报输出与已知容量支持扩容才改变额度。

下一轮重新加载策略，并用模型、路由、端点和模型配置的摘要校验待用恢复参数。恢复额度只用于对应的下一轮，不永久修改模型配置。修改配置后需重启后端以加载，当前未重启生产进程。

Debug 请求诊断增加最终线上的数字输出字段；恢复事件记录原因、策略和下一轮额度。记录不包含明文提示、代码、任意扩展参数或密钥。
