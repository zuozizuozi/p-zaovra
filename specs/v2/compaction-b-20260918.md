# B：压缩后的要求保留与失败处理

状态：B 本轮定向修复与 B2 验证完成，四份摘要重放全部通过。完整基线验收仍未全通过：B1 CSV 全通过，库存产物独立检查通过，但首次摘要失败、压缩前只读阶段越界；本轮未重新运行完整任务。见 [B1 实测报告](./experiments/compaction-b1-live-20260918.md)、[B2 定向重放](./experiments/compaction-b2-live-20260919.md)。

## 实现

1. 原文由宿主读取，不依赖模型摘要。每次构造压缩后请求时，按检查点序号从持久用户消息读取此前已提升的请求，按时间顺序放入同一个 conversation-checkpoint 的 original-user-requests。包括原始文本、后续修正、消息 ID 及附件引用；内嵌附件只保留引用说明，不重复塞入 base64。检查点之后的新消息沿用正常历史。没有重新提交 inbox、重排执行或恢复历史工具调用。
2. 原文、摘要和观察分开标注。原文是历史用户要求，后续修正优先；已经完成的要求不因再次出现而重新执行。生成摘要不能豁免要求或充当验证证据。数据仍由 SessionHistory 和原持久记录拥有，不增加第二份需求数据库或 public contract。
3. 摘要提交前校验固定章节的名称、顺序、非空叶节，以及常见工具调用标记。收到真正的工具调用事件也直接拒绝；摘要模型没有工具执行路径。只有正常结束且结构有效的摘要才发布 Compaction.Ended，保留原有用量记录和取消处理。
4. 结构错误、工具协议泄漏、摘要输入放不进配置上下文时发布 Compaction.Failed，保留旧上下文及旧有效检查点。同一自动压缩源的失败仍由持久事件抑制，手动压缩仍是显式操作。不增加新的重试循环。原请求还能执行时允许继续；提供方确认上下文超限且一次恢复无法解决时明确失败，说明历史未删除并给出扩大上下文或明确缩小任务的下一步。

为避免自行猜测任务边界，目前保留检查点之前本 Session 的全部已提升用户请求，不自动删除所谓过时任务。要求极长时会增加输入负担；不会承诺任意长度都能压缩进任意模型，也不会把粗略 Token 估计当作理由静默裁掉原文。附件内容不等同于已阅读或已验证。

结构校验不证明摘要语义正确；原文重新带入也不证明模型必然正确理解所有要求。本地测试验证的是数据保留、事件结算、拒绝路径和有限恢复，实际交付质量另需真实模型与独立判题。

实测后补充：摘要请求使用独立 system 指令限定摘要职责，归档任务作为 user 数据，防止两者混在同一指令层级。输入预算同时计入 system 指令。保留旧校验和输出额度，不加重试。B2 四份真实摘要重放均正常结束并通过校验，包含 B1 曾失败的请求；有限样本不证明所有模型都不会混淆职责。
