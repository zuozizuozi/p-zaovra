# 两次实机任务后的执行与验收修复方案

日期：2026-09-15。以下保留原审计与五步方案；实施结果及验证边界见文末。不能把计划中的验收项目自动视为已经验证。

## 结论与责任

造物改进.txt 将 Cline 定位为任务理解和验证闭环参考，将 Codex 定位为执行工程参考。codex-runtime-review.md 记录的实现包括共享 Shell 生命周期、取消、超时和输出保留；preflight-completion-review.md 中的 build/test/lint + snapshot 完成状态是 Zaovra 的本地设计，不能称为完整移植了任一竞品的验收机制。

已有机制有实际价值，但之前以组件测试和实现清单推断产品链路可用，结论超过证据。BYOK 通用性要求明确工具契约、保留真实执行证据和保守报告完成范围，不要求模型永不出错。

## 本次证据

- Windows 默认 shellCommand 选择 COMSPEC/cmd，PowerShell 单独采用 EncodedCommand。使用相同 Node 子进程 shell 调用形式复现：单行 node -e 输出 CHECK_RAN、退出 0；引号内包含换行的版本 stdout/stderr 为空、退出 0。该复现验证底层边界，实施时必须加入 AppProcess 和 V2 Bash 的整链路回归。
- 当前 Windows Shell 两项测试和 outcome 三项测试全部通过。多行场景只覆盖 PowerShell，cmd 只覆盖单行 type，未覆盖事故形态。
- system-context/builtins.ts 的环境基线上报平台和目录，没有实际选定的 Shell。Bash 描述说明配置/default，但没有随有效配置注入具体 Shell。
- outcome.ts 固定要求 build/test/lint，按 kind 覆盖检查记录，依据 exit 和 Location snapshot 判定。不能表达单文件游戏的语法、启动、交互检查，不能用项目快照证明桌面其他目录里的成品未变。
- 模型最终文字未强制绑定 outcome 的证据摘要。模型声称成功、todo 勾选、软件 completed_verified 是三种不同事实。两次事故不能据此断言软件当时给出了 completed_verified。
- 重复保护只统计连续、参数完全相同的工具调用。改引号或插入一次其他命令即可重置；这解释了为什么相近的失败验证可以反复发生，但不能凭无输出本身断定没有进展。
- 第一轮坏 JSON 留下 pending 并显示 interrupted 是历史已见事故。当前 runner 已有 failUnsettledTools，必须复现原始协议事件与退出路径再修，不能假定没有清理代码，也不能简单把所有 unknown 改成 failed。
- 第二轮成品最终可运行，暂停按住时逐帧切换。此前的语法错误和暂停问题是生成代码缺陷；执行层需提供有效验证手段并准确说明未验证范围。

## 顺序实施与验收

### 1. 修 Shell 契约和实际执行（P0）

位置：core/process.ts、core/tool/bash.ts、core/system-context/builtins.ts、core/test/process/windows-shell.test.ts。

统一解析有效 Shell，执行器、工具描述、环境上下文读取同一结果。Windows 未显式配置时优先选择可用 PowerShell 并使用现有编码调用；保留用户明确配置的 cmd，不暗中翻译为另一种语言。对 cmd 无法可靠承载的跨行引号输入明确拒绝并提供写脚本文件的纠正信息；合法多行脚本采用经测试的脚本文件调用方式，不能粗暴拼接换行。

验收：单/多行、中文和空格目录、单双引号、失败退出、无输出成功、超时和子进程清理通过真实 AppProcess 和 V2 Bash。检查预期副作用及输出，不仅检查 exit 0。事故输入不能再静默成功。无输出本身不判失败。

### 2. 修工具输入失败到最终状态的结算（P0）

位置：llm/protocols/utils/tool-stream.ts、core/session/runner/publish-llm-event.ts、runner/llm.ts、session/outcome.ts。

复放原始坏 JSON，追踪 input-start、参数解析、provider-error/Effect failure、Tool.Failed、Step.Failed 的路径。区分未执行的参数错误和已经开始、结果不确定的副作用。参数错误写终态及模型可读错误；允许有界纠正，不修猜 JSON，不自动重放有副作用的调用。保留原始参数/错误供诊断并限制展示长度。

验收：坏 JSON 不写文件、不留 pending，不误显示人工中断；正常用户取消仍 interrupted；真实崩溃仍 outcome unknown；恢复前核对现场，不能重复执行上次写入。

### 3. 让验收证据与本次成品对应（P0）

位置：schema/session-outcome.ts、core/tool/bash.ts、core/session/outcome.ts、core/snapshot.ts 的调用边界。

沿用现有检查记录，不另建 reviewer。记录检查对象、命令、退出结果、Evidence ID、产物版本/指纹及验证范围。项目任务根据实际脚本选择检查；HTML 游戏选择语法、启动、交互等适用检查，不能强迫所有任务凑 build/test/lint。按检查身份和对象保留结果，避免同种类的一次通过遮掉另一个对象的失败。外部目录成品需对应文件指纹；不能由无关项目快照背书。工具通过仅代表明确检查范围，不代表全部用户要求满足。

验收：语法错 HTML 不通过；修正后语法检查通过但未交互时仍明确未验证玩法；产物随后变更使旧检查失效；非 Git/外部目录有明确证据或保持未验证。输出带 ERROR 不一律失败、空输出不一律失败，进程测试需有可信断言；捕获异常并 exit 0 的坏测试不能靠字符串猜测修复。

### 4. 让最终报告和失败恢复使用同一证据（P1）

位置：core/session/runner/llm.ts、to-llm-message.ts、app-ui 的结果面板。

将紧凑的已执行检查/失败/未验证范围提供给模型，最终 UI 固定显示宿主记录的状态和证据，不让自由文本或 todo 覆盖它。不篡改模型原话，不承诺自动识别所有夸大表述。

保留现有步数上限和相同调用保护。先针对连续明确失败、明确未执行的验证增加有界纠正提示，要求换方法或报告阻碍；没有充分证据不把普通静默命令判成无进展。达到预算或已知硬限额时停止并保留状态，不继续自动重试同一请求。保留用户主动继续入口。

验收：模型说“全部通过”而证据缺失时，界面仍显示未验证；重复已知失败不会无提示耗尽轮次；正常多次修改测试不被误杀；修复失败必须保留原任务和已完成工作。

### 5. 以事故链路作为交付门槛（P1）

低层测试之外，在独立环境中从桌面 V2 消息入口走协议事件、工具执行、持久化和 UI。复放已捕获的模型响应可确定性验证软件，不消耗模型额度；真实模型测试另行标注，不能互相替代。

必测：多行检查静默返回 0、坏 JSON、错误吞掉却 exit 0、外部目录产物、验证后再改文件、免费额度耗尽、重启无重放，以及开头流式列表不闪烁。涉及公共 schema/API 时按仓库规则生成客户端；涉及界面时使用生产构建，保留修改前后指标。每项提交同时说明实现范围、验收证据和剩余边界。

## 范围约束

不引入强制第二模型、Computer Use、统一复杂评分器或大规模 Runtime 重构。浏览器/交互验收使用现有可用能力；缺少能力就如实标未验证。不能把本方案当作模型输出质量保证，优先保证执行真实、失败可解释、完成状态有证据。

## 本次实施结果

1. Shell：统一有效 Shell 解析，Windows 默认优先 PowerShell，环境上下文告诉模型具体 Shell。显式 cmd 的跨行命令在 AppProcess.run 执行前拒绝，要求改用脚本文件；未翻译命令。真实进程测试覆盖事故输入、Unicode/空格、空输出、退出码和超时清理，真实 Bash 注册链路验证脚本结果。
2. 工具结算：提供方流失败后，将未执行的本地 input-only 工具结算为 error，持久化回放后不会残留 pending；用户中断和未知副作用仍保留原语义。坏 JSON 直接停止并允许用户核对后继续，本次没有增加自动 JSON 修补或自动重放。
3. 验证记录：新增 syntax/smoke/interaction，保存 cwd、明确目标及 SHA-256 指纹，面板显示目标与 Evidence ID。记录按命令、种类和输入范围区分；独立 HTML 要求三个检查种类且目标仍匹配。普通项目读取已有 package.json 脚本；未识别的验收范围保留未验证。缺失、不可读或大于 64 MiB 的文件不能作为有效指纹证据。
4. 报告及停止：给模型提供已执行检查记录，并明确其尚未重新校验文件新鲜度；宿主面板独立显示完成状态和缺项。连续三次明确 Shell 失败后要求改变方法，四次后禁用工具并进入最终报告；成功检查、读取或编辑可解除计数。OpenRouter 每日免费额度耗尽不再自动重试，普通临时限流保留既有重试。
5. 回归：已运行真实 Windows 进程/Bash、V2 runner 持久化与恢复、原始 OpenAI Chat 事件解析、验证状态、Evidence 读取及生产构建下的 UI 回归。客户端与旧 SDK 已按要求生成，Core/LLM/Schema/Client/App UI 类型检查通过。

### 验证记录与范围

- Core：139 项通过，覆盖九个测试文件，包括取消/恢复、失败工具结算及变化参数不能绕过四次失败限制。
- LLM：48 项通过，覆盖 OpenAI Chat、tool-stream 和 executor；坏 JSON 不产生可执行 tool-call，硬额度错误不重试。
- UI：3 项通过，覆盖启动阶段流式布局、格式化列表保留、模型自称全通过但宿主仍显示未验证。
- 生产 UI 性能，同机 CPU 4 倍降速、40 个增量、12 轮历史：完成 10560.9 → 10602.4 ms（约 +0.4%）；首内容 261.5 → 243.2 ms；P95 帧间隔 16.7 → 16.8 ms。前后空白采样和滚动漂移为零，消息与 Markdown 节点未重建。仅一次前后样本，且基线可能受其他检查负载影响，不能宣称细微性能改善或排除所有回退。

### 尚未证明的边界

- 这是分层串联覆盖，不是一次从真实 Electron 输入框经真实 HTTP 提供方、Shell、数据库到 UI 的完整自动化运行；没有使用用户 Key 或消耗额度，也没有重启用户应用。
- 检查标签由 Agent 提供，宿主记录实际命令、退出码和目标版本，不会判断任意脚本是否真正覆盖玩法。吞异常后 exit 0 的脚本仍可能提供薄弱证据；不能据此宣布全部用户要求通过。
- HTML 的三类检查规则适用于显式声明目标的独立页面，不是任意语言、混合项目或全部产物依赖的通用验收规划器。未列出的依赖文件不受单文件指纹保护。
- 没有自动修改用户游戏，也没有新增浏览器控制能力或第二模型 reviewer。缺少实际交互检查时应明确保留未验证；人工实机仍是下一道验收。
